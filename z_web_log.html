🔗 2026-09-02 15:51 — 訪談變慢調查：MiniMax-M2.5 vs M3 實測時間比較，最終改回 M2.5

欄位內容
類型模型調整 / 效能調查（非 app chat 紀錄，串連本頁下方 4 筆真實請求的耗時數據）

結論MODEL 常數維持 MiniMax-M2.5；LLM_MAX_CONCURRENCY 6→10 保留

調查過程

1) 用 z_web_log.html 歷史「回覆所需時間」欄位確認退化屬實（5-6 月穩定 80-170 秒，9/2 飆到 540 秒），排除程式碼變更（lib/ 自 5/30 起無 commit）與 MiniMax API 全域降速（單筆呼叫 1.3 秒、6 併發真實 prompt 也無 429）。2) 找到根因：MiniMax 同 prompt 併發下輸出 token 數變異極大（506～1690 token，3.3 倍差距），導致批次內「等最慢的那個」造成拖累；曾嘗試調降 max_tokens（2500→1400/1800）逼模型精簡，但 10 併發實測顯示～20% 回應被截斷、且截斷的正是最慢的那幾筆，此招對症無效已復原。3) 改提高 LLM_MAX_CONCURRENCY 6→10（實測 0 個 429），30 位受訪者從 5 批降到 3 批。4) 查詢 MiniMax 可用模型清單，發現 M3（比目前用的 M2.5 新）；10 次孤立合成測試顯示 M3 更快（19s vs 25s、0 截斷）且 output 定價相同（$1.20/M），改用並實測。

M3 真實 pipeline 表現不如預期

孤立合成測試（單一 bundled JSON 訪談 prompt、無 PM 規劃/報告階段）預測 M3 較快，但真實跑完整 pipeline（30 受訪者 + PM 規劃/報告 + retry 機制）反而比 M2.5 慢近 2 倍。log 顯示 M3 觸發：PM 報告輸出被截斷重試 1 次、2 位受訪者 bundled JSON 格式失敗退回慢速逐題模式（1 次呼叫變 6 次序列呼叫）。判斷 M3 對本專案的 bundled JSON 格式指令遵循度比 M2.5 差，一旦格式跑掉就吃 fallback 稅金，抵銷甚至反超原本的速度優勢。已改回 MiniMax-M2.5，並在 lib/anthropic.ts MODEL 常數旁留註解記錄此教訓：換模型的合成 benchmark 測不出格式遵循度風險，須用真實 pipeline 驗證。

保留的變更

LLM_MAX_CONCURRENCY 6→10（.env.local，未進 git）；lib/anthropic.ts MODEL 註解記錄本次實驗結論；lib/agents/persona.ts 的 max_tokens 復原為 2500 並加註解說明調小無效的原因。
